# Безпека

Цей документ описує, як влаштована безпека демо-стенда, куди рухаються дані і
що саме треба закрити перед продакшеном. Він написаний чесно: демо має відомі
спрощення, і вони перелічені явно, а не сховані.

---

## 1. Головне застереження

**Демо не має шару автентифікації.** API на `demax.kindrakevich.com/api`
відкритий: будь-хто, хто знає адресу, може надіслати запит до асистента чи
прочитати переклади інтерфейсу. Це свідомий компроміс стенда для показу.

Специфікація (Backend API §2) вимагає для продакшену:

- JWT з підписом RS256, ключ у менеджері секретів, ніколи не в базі;
- для персоналу — email + пароль (Argon2id) + обов'язкова MFA (TOTP);
- для клієнтів — прив'язка Telegram-акаунта через OTP по телефону;
- перевірку прав на рівні рядків: менеджер бачить лише свій портфель, чужі
  записи повертаються як `404`, а не `403`, щоб не розкривати їхнє існування;
- відкликання токенів через denylist за `jti`.

Нічого з цього в демо немає. Це перше, що реалізується у Фазі 1.

## 2. Секрети

| Що | Де зберігається | Як захищено |
|---|---|---|
| Ключ LLM-провайдера | `demax-rag/.env` на сервері | `chmod 600`, у git не потрапляє |
| Пароль до бази | той самий `.env` | згенерований випадково, не повторює інші паролі |
| SSH-ключ деплою | GitHub Secrets | зашифрований, у логах не з'являється |
| IP і шлях на сервері | GitHub Secrets | не хардкодяться в коді |

`.gitignore` виключає `.env`, `*.pem`, `*.key`, теку `secrets/`, а також
матеріали замовника (`*.docx`, специфікації) і внутрішні комерційні розрахунки.

**Перевірка перед публікацією.** Репозиторій сканувався не лише в поточному
стані, а по всій історії комітів — на патерни ключів (`sk-`, `AIza`, `ghp_`,
`BEGIN PRIVATE KEY`) і на випадково додані файли. Історія чиста, бо `.gitignore`
з'явився до першого коміту.

> У `docker-compose.yml` і дефолті `db.py` є пара `demax:demax` — це логін
> локального контейнера для розробки, який існує тільки на машині розробника.
> Прод використовує згенерований пароль із серверного `.env`.

## 3. Потоки даних: що залишає периметр

Це найважливіший розділ для замовника, який питає «а куди йдуть наші дані».

### Залишається всередині

- **Уся база знань.** Ембедінги рахуються локально моделлю ONNX, без жодного
  мережевого виклику. Тексти сторінок і каталогу нікуди не надсилаються.
- **Історія розмов.** Зберігається у власному PostgreSQL, доступному лише з
  `127.0.0.1`.
- **Переклади інтерфейсу.** Власна таблиця, власна база.

### Виходить назовні (до LLM-провайдера)

| Сценарій | Що надсилається |
|---|---|
| Відповідь консультанта | запитання користувача + до 5 знайдених фрагментів бази знань + до 6 попередніх реплік розмови |
| AI-звіт по системі (⌘K) | запит менеджера + агрегований зріз показників (кількості, а не персональні картки) |

Обсяг обмежений навмисно: моделі передається рівно те, що потрібно для
відповіді, а не вся база. Провайдер замінюваний — код звертається до нього
через єдину функцію, тож перехід на локальну модель не зачіпає решту системи.

### Персональні дані

База знань зібрана з публічних сторінок сайту та каталогу — персональних даних
у ній немає за побудовою. Клієнти в демо вигадані. У продакшені специфікація
(DBSPEC §7.4) вимагає GDPR-каскаду стирання, тombstone-полів для вільного
тексту й збереження редагованих аудит-записів.

> ⚠️ **Зріз для AI-звітів формується на клієнті.** У демо браузер надсилає
> показники разом із запитом. У продакшені це має робити сервер, читаючи дані
> під роль користувача — інакше клієнт може підмінити цифри у звіті або
> запросити показники поза своїм портфелем.

## 4. Мережа й доступи

- **Публічно назовні** дивиться лише Nginx (порти 80/443) за Cloudflare.
  PostgreSQL і API слухають `127.0.0.1` і ззовні недосяжні.
- **CORS** обмежений доменом демо, а не `*`.
- **TLS** термінує Cloudflare; між Cloudflare і сервером — origin-сертифікат.
- **Доступ до сервера** — лише за SSH-ключем.

## 5. Захист від типових атак

| Вектор | Що зроблено |
|---|---|
| SQL-ін'єкції | усі запити параметризовані, конкатенації рядків із даними користувача немає |
| XSS через відповідь моделі | Markdown рендериться власною функцією, яка **спершу екранує HTML**, а вже потім застосовує форматування — тег у відповіді моделі показується як текст, а не виконується |
| Витік ключа в браузер | ключі живуть лише на сервері; фронтенд ходить на власний домен, ключів не бачить |
| Перевантаження запитами | ⚠️ **відсутнє** — rate limiting не реалізовано (див. §7) |
| Clickjacking, MIME-sniffing, downgrade до HTTP | заголовки `X-Frame-Options`, `X-Content-Type-Options`, `HSTS` і `Content-Security-Policy` віддаються Nginx (конфігурація — у [DEPLOY.md](DEPLOY.md) §3.2) |
| Prompt injection через базу знань | ⚠️ **частково** — база складається з контенту самого бренду; для чужих джерел потрібна ізоляція інструкцій |

## 6. Поведінка AI як питання безпеки

Асистент навмисно обмежений, і це теж елемент безпеки — репутаційної:

- відповідає лише з бази знань; коли даних немає, каже про це прямо, а не
  вигадує;
- **скарги ескалюються детерміновано в коді**, а не на розсуд моделі — модель
  у тестах інколи бралася відповідати на претензію, тож це рішення винесене з
  промпту в код;
- медичні питання й комерційні рішення (ціни, опт, повернення) також ідуть до
  менеджера;
- у відповідях показуються джерела — користувач бачить, звідки взято факт.

## 7. Що треба закрити перед продакшеном

Перелік свідомих спрощень демо. Це не «баги», а межа стенда:

1. **Автентифікація і права** — JWT, MFA, перевірка на рівні рядків (§1). Без
   цього систему не можна показувати реальним користувачам.
2. **Rate limiting** — специфікація визначає ліміти на клієнта, на OTP і на
   повідомлення до AI; у демо їх немає.
3. **Аудит-лог** — таблиця в специфікації описана як append-only з відкликаними
   правами на UPDATE/DELETE; у демо аудит показаний в інтерфейсі, але не
   пишеться.
4. **Зріз для AI-звітів на сервері** замість клієнта (§3).
5. **Бекапи з перевіркою відновлення** — PITR налаштовується в aaPanel, але
   регулярні тестові відновлення треба ввести в регламент.
6. **Ротація ключів** — і за розкладом, і негайно при підозрі на витік.
7. **AV-сканування завантажених дипломів** перед прийманням заявки
   (специфікація §7).
8. **Ролі в базі з мінімальними правами** — застосунок ходить у базу від
   власника схеми; у продакшені міграції й робота застосунку розділяються на
   різні ролі, щоб скомпрометований процес не міг змінити схему.

Уже зроблено: заголовки безпеки (HSTS, CSP, X-Frame-Options,
X-Content-Type-Options, Referrer-Policy) віддаються Nginx, PostgreSQL і API
слухають лише `127.0.0.1`, `.env` має права `600`.

## 8. Якщо ключ скомпрометовано

1. Відкликати ключ у провайдера — це швидше, ніж будь-що інше.
2. Випустити новий, оновити `demax-rag/.env` на сервері, перезапустити сервіс:
   `systemctl restart demax-rag`.
3. Якщо ключ бував у git — переписати історію недостатньо: GitHub зберігає
   об'єкти в кеші. Ключ вважається зламаним назавжди, потрібна саме заміна.
4. Перевірити журнал використання у провайдера на чужу активність.
